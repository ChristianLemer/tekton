# CAPTURE

*"I have a task."*

**Intention:** Add a task to the backlog without friction.

**When:** The human signals a task — rough, dictated, in passing — or a stream item (mail, message, notification) carries a commitment.

**Input:** Free expression from the human, or a stream item and its identifier.

**Output:** Task created in the reservoir, state `waiting` — as an issue, a file, or whatever the provider uses — with its source when it has one.

**Sequence:**
1. The human signals the task.
2. From a stream: is it a commitment that takes work? A stream state is not a task — a short reply stays in the stream. One task per commitment, not per message.
3. From a stream: is the source already linked to a task? The known identifier decides, not a similar title. If so, do not capture again.
4. The guardian identifies the partition and nature (one-off, rhythm, worksite).
5. The guardian creates the task in the reservoir (mapped to the partition's project/label/folder), state `waiting`; a task from a stream records its source, and the source points back where it can.
6. The guardian confirms.

**Guardrails:** No form, no friction. If the partition or nature is ambiguous, the guardian asks — it doesn't guess. Do not capture and allocate at the same time — they are different gestures with different cognitive modes. **A stream state is not a task**: capturing every flagged message turns the backlog into a duplicate of the stream. If it is not obvious whether an item is a commitment, ask.

**Source method:** Kairos.
